# Technical Details: How DisableProvisioning Works with Existing Objects

## Executive Summary

**YES**, the implementation will work with already-existing database objects. The sync process **references** existing stored procedures, triggers, and tracking tables by name rather than creating them.

However, **all required objects must exist** before sync starts, or the sync will fail with SQL exceptions.

---

## How Dotmim.Sync Uses Database Objects During Sync

### 1. Stored Procedures - Reference by Name Only

**Key Finding:** Dotmim.Sync does NOT check if stored procedures exist during sync. It simply calls them by name.

**Evidence from `SqlSyncAdapter.cs` (lines 59-189):**

```csharp
public override (DbCommand, bool) GetCommand(SyncContext context, DbCommandType commandType, SyncFilter filter)
{
    using var command = new SqlCommand();
    switch (commandType)
    {
        case DbCommandType.SelectChanges:
            command.CommandType = CommandType.StoredProcedure;
            // Just sets the NAME - doesn't check if it exists!
            command.CommandText = this.SqlObjectNames.GetStoredProcedureCommandName(
                DbStoredProcedureType.SelectChanges, filter);
            break;
        // ... similar for UpdateRow, DeleteRow, etc.
    }
    return (command, isBatch);
}
```

**Process:**
1. Creates a SqlCommand object
2. Sets `CommandText` to the stored procedure name (e.g., `[dbo].[ProductCategory_selectchanges]`)
3. Sets `CommandType` to `StoredProcedure`
4. Later calls `DeriveParameters()` to get parameter metadata from the database

**From `SqlSyncAdapter.cs` line 267:**
```csharp
((SqlConnection)connection).DeriveParameters((SqlCommand)command, false, (SqlTransaction)transaction);
```

This queries the database to get parameters from the **existing** stored procedure.

**What happens if the SP doesn't exist?**
- SQL Server will throw: `"Could not find stored procedure 'dbo.ProductCategory_selectchanges'"`
- The sync will fail immediately

---

### 2. Tracking Tables - Used via SQL Commands

**Key Finding:** Tracking tables are referenced in SQL queries generated by stored procedures and triggers.

**Evidence from stored procedure pattern:**
```sql
-- Example: SelectChanges stored procedure references tracking table
CREATE PROCEDURE [dbo].[ProductCategory_selectchanges]
AS
BEGIN
    SELECT ...
    FROM [dbo].[ProductCategory] t
    LEFT JOIN [dbo].[ProductCategory_tracking] side ON ...
    WHERE side.timestamp > @sync_min_timestamp
END
```

**The tracking table is used by:**
- Triggers (INSERT/UPDATE/DELETE) to record changes
- SelectChanges stored procedures to retrieve changes
- Update/Delete stored procedures to update tracking metadata

**What happens if tracking table doesn't exist?**
- First stored procedure call will fail
- SQL Server will throw: `"Invalid object name 'dbo.ProductCategory_tracking'"`

---

### 3. Triggers - Fire Automatically on Data Changes

**Key Finding:** Triggers are NOT called directly by Dotmim.Sync. SQL Server fires them automatically.

**Trigger Pattern:**
```sql
CREATE TRIGGER [ProductCategory_insert_trigger]
ON [dbo].[ProductCategory]
AFTER INSERT
AS
BEGIN
    -- Automatically writes to tracking table
    INSERT INTO [dbo].[ProductCategory_tracking] (...)
    SELECT ... FROM INSERTED
END
```

**What happens if triggers don't exist?**
- Data changes on the server won't be tracked
- Client won't receive updates on next sync
- **Silent data loss** - this is dangerous!

---

### 4. Scope Info Tables - Direct Queries

**Key Finding:** Scope info tables (`scope_info` and `scope_info_client`) are queried directly.

**Evidence from `BaseOrchestrator.ScopeInfos.cs` line 227:**
```csharp
using var command = scopeBuilder.GetCommandAsync(
    DbScopeCommandType.GetScopeInfo, runner.Connection, runner.Transaction);
```

This generates SQL like:
```sql
SELECT * FROM [dbo].[scope_info]
WHERE [sync_scope_name] = @sync_scope_name
```

**What happens if scope_info tables don't exist?**
- Sync initialization will fail immediately
- SQL Server will throw: `"Invalid object name 'dbo.scope_info'"`

## Validation and Checks

### During Provisioning (Skipped with DisableProvisioning = true)

**Object Existence Checks (NOT EXECUTED when DisableProvisioning = true):**

From `BaseOrchestrator.StoredProcedures.cs` line 412:
```csharp
internal async Task<(SyncContext, bool)> InternalExistsStoredProcedureAsync(...)
{
    var existsCommand = await tableBuilder.GetExistsStoredProcedureCommandAsync(
        storedProcedureType, filter, connection, transaction);
    // Executes: SELECT COUNT(*) FROM sys.procedures WHERE name = @name
    // ...
}
```

Similar checks exist for:
- `InternalExistsTrackingTableAsync()`
- `InternalExistsTriggerAsync()`
- `InternalExistsScopeInfoTableAsync()`

**IMPORTANT:** These checks only run during provisioning. With `DisableProvisioning = true`, they are **completely skipped**.

### During Sync Operations (Always Executed)

**NO pre-flight validation checks!**

The sync process assumes all objects exist and will fail immediately when trying to:
1. Call a missing stored procedure → SQL exception
2. Query a missing tracking table → SQL exception (via stored procedure)
3. Read from missing scope_info table → SQL exception

## What Objects Are Required?

### For Each Synced Table (e.g., "ProductCategory")

**1. Base Table** (if provisioning with `SyncProvision.Table`)
```sql
[dbo].[ProductCategory] -- Your actual data table
```

**2. Tracking Table** (always required)
```sql
[dbo].[ProductCategory_tracking] -- Tracks changes with timestamps
```

**3. Triggers** (always required)
```sql
[dbo].[ProductCategory_insert_trigger]
[dbo].[ProductCategory_update_trigger]
[dbo].[ProductCategory_delete_trigger]
```

**4. Stored Procedures** (always required)

For **server** (download-only scenario):
```sql
[dbo].[ProductCategory_selectchanges]              -- Get changes since last sync
[dbo].[ProductCategory_selectchanges_filtered]     -- Get changes with filters (if using filters)
[dbo].[ProductCategory_initialize]                 -- Initial sync
[dbo].[ProductCategory_initialize_filtered]        -- Initial sync with filters
[dbo].[ProductCategory_update]                     -- Apply client changes (if bi-directional)
[dbo].[ProductCategory_delete]                     -- Delete rows
[dbo].[ProductCategory_deletemetadata]             -- Cleanup metadata
[dbo].[ProductCategory_reset]                      -- Reset tracking
-- Plus bulk operations if using UseBulkOperations = true
```

For **client** (download-only):
```sql
-- Same as server, even for download-only
-- The framework tries to call these, but download-only providers return null for upload SPs
```

**5. Table Types** (if using bulk operations)
```sql
[dbo].[ProductCategory_BulkType] -- User-defined table type for bulk inserts/updates
```

### Global Objects (Once per database)

```sql
[dbo].[scope_info]         -- Server scope metadata
[dbo].[scope_info_client]  -- Client scope metadata (on client database)
```

## Failure Scenarios and Error Messages

### Scenario 1: Missing Stored Procedure

**Symptom:**
```
Microsoft.Data.SqlClient.SqlException:
Could not find stored procedure 'dbo.ProductCategory_selectchanges'.
```

**When it happens:** First sync attempt, during GetChanges operation

**Fix:** Create the missing stored procedure via migration script

---

### Scenario 2: Missing Tracking Table

**Symptom:**
```
Microsoft.Data.SqlClient.SqlException:
Invalid object name 'dbo.ProductCategory_tracking'.
```

**When it happens:**
- During SelectChanges (inside stored procedure)
- During trigger execution (on data modification)

**Fix:** Create the missing tracking table via migration script

---

### Scenario 3: Missing Triggers

**Symptom:**
- No error messages
- Sync completes successfully
- **But changes aren't tracked!**

**When it happens:**
- Data is modified on server
- Trigger doesn't exist to record change
- Next sync doesn't include the change

**Fix:** Create ALL three triggers (INSERT, UPDATE, DELETE) via migration script

**This is the most dangerous scenario** - silent data loss!

---

### Scenario 4: Missing scope_info Table

**Symptom:**
```
Microsoft.Data.SqlClient.SqlException:
Invalid object name 'dbo.scope_info'.
```

**When it happens:** Very first operation, during scope initialization

**Fix:** Create scope_info and scope_info_client tables via migration script

---

### Scenario 5: Schema Mismatch

**Symptom:**
```
Microsoft.Data.SqlClient.SqlException:
The multi-part identifier "dbo.ProductCategory_tracking.NewColumn" could not be bound.
```

**When it happens:**
- Server schema was updated
- Client migration scripts are outdated
- Stored procedures reference columns that don't exist in client tracking table

**Fix:**
- Regenerate migration scripts from latest server schema
- Apply updated scripts to client database

## Validation Recommendations

### Before Deploying Client with DisableProvisioning = true

**1. Create a validation script:**

```sql
-- Validate all required objects exist
DECLARE @MissingObjects TABLE (ObjectType VARCHAR(50), ObjectName VARCHAR(255))

-- Check tracking tables
IF NOT EXISTS (SELECT * FROM sys.tables WHERE name = 'ProductCategory_tracking')
    INSERT INTO @MissingObjects VALUES ('Table', 'ProductCategory_tracking')

-- Check triggers
IF NOT EXISTS (SELECT * FROM sys.triggers WHERE name = 'ProductCategory_insert_trigger')
    INSERT INTO @MissingObjects VALUES ('Trigger', 'ProductCategory_insert_trigger')
IF NOT EXISTS (SELECT * FROM sys.triggers WHERE name = 'ProductCategory_update_trigger')
    INSERT INTO @MissingObjects VALUES ('Trigger', 'ProductCategory_update_trigger')
IF NOT EXISTS (SELECT * FROM sys.triggers WHERE name = 'ProductCategory_delete_trigger')
    INSERT INTO @MissingObjects VALUES ('Trigger', 'ProductCategory_delete_trigger')

-- Check stored procedures
IF NOT EXISTS (SELECT * FROM sys.procedures WHERE name = 'ProductCategory_selectchanges')
    INSERT INTO @MissingObjects VALUES ('StoredProcedure', 'ProductCategory_selectchanges')
IF NOT EXISTS (SELECT * FROM sys.procedures WHERE name = 'ProductCategory_selectchanges_filtered')
    INSERT INTO @MissingObjects VALUES ('StoredProcedure', 'ProductCategory_selectchanges_filtered')
-- ... check all other required SPs ...

-- Check scope tables
IF NOT EXISTS (SELECT * FROM sys.tables WHERE name = 'scope_info')
    INSERT INTO @MissingObjects VALUES ('Table', 'scope_info')
IF NOT EXISTS (SELECT * FROM sys.tables WHERE name = 'scope_info_client')
    INSERT INTO @MissingObjects VALUES ('Table', 'scope_info_client')

-- Report results
IF EXISTS (SELECT * FROM @MissingObjects)
BEGIN
    SELECT ObjectType, ObjectName FROM @MissingObjects
    RAISERROR('Missing required Dotmim.Sync objects!', 16, 1)
END
ELSE
    PRINT 'All required objects exist'
```

**2. Run this validation:**
- After applying migration scripts
- Before deploying client application
- In your CI/CD pipeline

---

### Runtime Validation (Optional)

You can add a custom validation before sync:

```csharp
var clientProvider = new SqlSyncProvider(clientConnectionString);
var options = new SyncOptions { DisableProvisioning = true };

// Optional: Validate objects exist before sync
await ValidateProvisionedObjectsAsync(clientProvider);

// Proceed with sync
var agent = new SyncAgent(clientProvider, serverOrchestrator, options);
var result = await agent.SynchronizeAsync();
```

**Validation method:**
```csharp
async Task ValidateProvisionedObjectsAsync(SqlSyncProvider provider)
{
    using var connection = provider.CreateConnection();
    await connection.OpenAsync();

    // Check if key objects exist
    var checkQuery = @"
        SELECT COUNT(*)
        FROM sys.tables
        WHERE name IN ('ProductCategory_tracking', 'scope_info', 'scope_info_client')
    ";

    using var cmd = connection.CreateCommand();
    cmd.CommandText = checkQuery;
    var count = (int)await cmd.ExecuteScalarAsync();

    if (count < 3)
        throw new Exception("Required sync objects are missing. Run migrations first!");
}
```

## Best Practices

### ✅ DO

1. **Generate migration scripts from server schema**
   - Provision a test database with full permissions
   - Script out all created objects
   - Version control these scripts

2. **Validate objects exist before sync**
   - Run validation scripts in CI/CD
   - Add optional runtime checks

3. **Test on a staging environment first**
   - Apply migrations to staging client database
   - Run test sync with DisableProvisioning = true
   - Verify all operations work

4. **Keep client and server schemas in sync**
   - When server schema changes, regenerate client scripts
   - Deploy updated scripts before new client version

5. **Use schema-qualified names**
   - Always specify schema: `[Report].[ProductCategory]`
   - Ensure all objects are in the correct schema

### ❌ DON'T

1. **Don't skip trigger creation**
   - Missing triggers = silent data loss
   - Always create all three triggers (INSERT/UPDATE/DELETE)

2. **Don't assume objects exist**
   - Always validate in deployment pipeline
   - Don't rely on error messages at runtime

3. **Don't mix provisioning modes**
   - Either use DisableProvisioning everywhere, or nowhere
   - Don't provision some tables and pre-provision others

4. **Don't modify object structure manually**
   - Always regenerate from server schema
   - Manual changes will cause schema mismatch errors

---

## Summary

| Aspect | Status | Details |
|--------|--------|---------|
| **Works with existing objects?** | ✅ YES | References objects by name, doesn't create them |
| **Validates objects exist?** | ⚠️ NO | Only during provisioning (which is skipped) |
| **Fails gracefully?** | ❌ NO | Immediate SQL exception if object missing |
| **Schema mismatch detection?** | ❌ NO | Fails at runtime with cryptic SQL errors |
| **Trigger validation?** | ❌ NO | **Silent failure - data loss possible!** |

**Conclusion:**

The implementation **will work** with pre-provisioned objects, BUT you must:
1. Ensure **ALL** required objects exist before sync
2. Keep schemas synchronized between server and client
3. Validate deployments before going to production
4. **Never skip trigger creation** - this causes silent data loss

The `DisableProvisioning = true` flag is **safe and effective** when used properly with validated migrations.
